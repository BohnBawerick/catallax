# Milestone releases

Catallax releases follow completed work, not dates. M1 is **0.1.0**. Each later roadmap milestone advances the minor version, so M2 is 0.2.0 and M3 is 0.3.0. Patch versions, such as 0.1.1, fix an already released milestone without claiming the next milestone. The entire 0.x series is labelled **alpha** and published as GitHub prereleases. A version number never encodes a date. The first 1.x release needs a separate readiness decision.

No release is scheduled by this machinery. A maintainer pushes a `vX.Y.Z` tag only after the checklist passes. The tag must match `workspace.package.version` in `Cargo.toml` and point to a commit reachable from the matching `release/X.Y.Z` branch. Do not move a published tag. Fix a bad release with a new patch version.

## Downloads

`cargo-dist` 0.33.1 packages the existing CLI crate. Each archive contains `catallax`, `catallax-verify`, the existing `exact-brep` compatibility program, README and MIT licence.

| Platform | Artifact |
| --- | --- |
| Linux x86_64, glibc | `catallax-cli-x86_64-unknown-linux-gnu.tar.xz` |
| Linux aarch64, glibc | `catallax-cli-aarch64-unknown-linux-gnu.tar.xz` |
| macOS universal, arm64 and x86_64 | `catallax-cli-universal2-apple-darwin.tar.xz` |
| macOS arm64 | `catallax-cli-aarch64-apple-darwin.tar.xz` |
| macOS x86_64 | `catallax-cli-x86_64-apple-darwin.tar.xz` |
| Windows x64 | `catallax-cli-x86_64-pc-windows-msvc.zip` |

Linux x86_64 builds on Ubuntu 22.04; aarch64 builds on Ubuntu 24.04. These are dynamically linked glibc builds, not musl binaries. Older glibc compatibility is not claimed. Platform jobs extract the archives and run the actual commands, build a block, export STEP and replay the portable question with identical STEP bytes. The universal job joins the two macOS builds with `lipo`, checks both slices with `lipo FILE -verify_arch arm64 x86_64` and exercises each through `arch` on Apple Silicon with Rosetta.

macOS downloads are not Developer ID signed or notarized. The universal executables use only the ad-hoc signature needed for Apple Silicon execution. Windows downloads are not Authenticode signed. GitHub provenance attestations do not replace platform code signing. No crates.io, package-manager or SolidDraft release is part of this workflow.

Every release also attaches:

- `catallax-cli.cdx.xml`, a dependency SBOM generated by cargo-cyclonedx 0.5.9 across all targets. `sbom.py` replaces machine-local workspace references with commit-qualified repository IDs and checks that dependency edges still resolve.
- `replay-summary.json`, a generated 477-input aggregate, with baseline and candidate commit identities, binary hashes, outcomes, work, preservation results and the committed upgrade-list digest.
- `target-parts.json`, generated at the tagged commit with the fixed 1,000,000-unit allowance and OpenCASCADE STEP imports.
- `RELEASE_NOTES.md`, generated from merged pull requests by GitHub's release-notes generator, with alpha, format-compatibility and verification notices. Do not maintain a hand-edited CHANGELOG.
- `SHA256SUMS`, covering all other attached files. Every attached file, including `SHA256SUMS`, gets a GitHub build-provenance attestation.

Verify an individual download with `gh attestation verify FILE --repo BohnBawerick/catallax`. After downloading all assets, run `sha256sum --check SHA256SUMS`, or use an equivalent SHA-256 tool on macOS or Windows. Hashes detect corruption; verify provenance to establish which repository and workflow built the file.

## Release checklist

1. Complete the milestone's must-show list in [PLAN section 10.1](PLAN.md#101-milestones). Record every in-flight lane as landed or parked. At the release freeze, record the exact candidate commit and create `release/<version>` from it. Development continues on `main`.
2. Set the workspace version and refresh `Cargo.lock` with Cargo on the release branch. No milestone bump is made merely to install the machinery.
3. Add `docs/milestones/MN.md`, such as `M1.md`, as required by PLAN item 21. Record landed and parked work, reasons, P0 and target-part numbers including regressions, and the next milestone's must-show list. Patch releases update that milestone's note.
4. Commit the version and milestone note on the release branch. Require a green full-suite `check.yml` push run on that exact commit and matching release branch. The tag workflow rejects a commit without one.
5. On the replay machine, build baseline and candidate verification programs and use the verification driver for the full 477 inputs. Preserve every earlier answer's manifest and strict output bytes except an explicitly approved transition described below; preserve the original inputs and work allowances without exceptions. Run baseline at one worker and the same candidate binary freshly at one, two and four workers. No cache hits, missing manifests or internal errors are allowed. Candidate worker runs remain strictly equal, with no approval exceptions.
6. Generate the public aggregate as below, then run the evidence workflow on the exact candidate commit. It generates the target scoreboard independently in CI. Inspect refusals, edits, STEP imports and not-run checks; the scoreboard is not proof of complete SolidDraft acceptance.
7. Run the non-publishing release dry run against that commit and evidence run. Inspect all platform smoke checks, SBOM, generated notes, checksums and attestations. Link the green run in the release preparation PR or milestone review.
8. Only then create and push the release tag from the checked release commit. Watch the release workflow. It publishes only after every platform, universal archive, evidence gate and attestation succeeds.

Measurement, comparisons and evidence aggregation live in scripts and CI. None runs in the kernel's part-building path or adds work to a user edit. Never increase a work allowance or loosen a tolerance to make a release gate pass.

The freeze holds release scope, not `main`. Finish exact-pin application acceptance, package dry runs and downloaded-build smoke on the versioned release branches. A blocker fix lands on `main` through its owning lane first, then is cherry-picked to the release branch, unless it applies only to the release. Record each resulting candidate commit and repeat affected exact-source evidence. Release CI has priority; report a starved release queue to the integration owner rather than cancel other lanes' work.

For an `X.Y.0` milestone release, use the previous release tag as the replay baseline. When no earlier release exists, use the candidate commit immediately before the version-and-milestone-note merge, the release commit's first parent. That first-release merge must change only release metadata and documentation, not kernel code or recipes. Record the selected baseline and why in the milestone review. Per-change preservation replays remain the cumulative evidence for the kernel work preceding that baseline.

Every changed baseline case must be either a reviewed refusal-to-answer upgrade in `tools/release/replay-upgrades.json` or an enumerated correction in `tools/release/replay-corrections.json`: an invalid-to-valid STEP correction, a same-code refusal-stage move or a captain-reviewed refusal change. Both files must be committed. Refusals that change code, answers becoming refusals, unexplained successful-answer changes and unlisted differences fail. Each list must describe exactly its used approvals, with no duplicate or overlapping positions and no unused entries. An empty list approves nothing.

### Joint SolidDraft release handoff

A qualified kernel merge is an intermediate result, not application acceptance. After kernel qualification, the release integration owner updates SolidDraft's dependency pins and lockfile once. Record the kernel commit, the SolidDraft commit containing that pin, the qualification tier and evidence links in the release review. Do not force the repositories to share a version number. Until the complete M2 must-show list passes, a patch of the completed milestone does not claim M2 or full canonical P1.

Run the final kernel evidence and package dry run at the exact candidate commit. Then check that SolidDraft's recorded pin is that same commit and complete its [application release checklist](https://github.com/BohnBawerick/soliddraft/blob/main/docs/RELEASING.md), including downloaded desktop and browser interaction, older supported documents, edited-part output and drawing reopen. Source changes after qualification require the affected evidence again. A successful kernel scoreboard or archive smoke does not certify the application's click, proof or output path.

The joint ordinary-parts cut requires the application bracket, edited collar, safe-edit recovery, checked exports and requested drill-point measurement, plus the rounded-boss correctness assessment for all affected shipped paths. Canonical P1 remains a separate full-path gate. Missing acceptance evidence or an unresolved shared-output correctness defect holds the tag; neither a deadline nor a passing package job overrides that hold.

The correction mechanism below is release-only and does not infer validity from differing bytes. The captain must approve the enumerated correction list and its retained independent evidence before it lands. Ordinary merges and nightly audits use one fixed replay configuration, including driver and comparator changes. Full baseline/candidate 1/2/4 qualification belongs only to a milestone-closing release and is reused when the kernel pin is unchanged. A previously accepted source change or a reader's healed import is not per-case approval. Do not change the baseline, relax the ordinary strict comparator or relabel a historical dry run to bypass this gate.

The [review inventory](../tools/release/review-candidates.json) records the 118 changes observed between v0.1.0 and the first 0.1.1 candidate. It is historical: the release gate does not read it and it approves nothing. Its three-output fingerprints omit IGES. The 0.1.1 approval files were generated instead from a fresh replay of the merged candidate. That replay covers 359 changed cases: 32 refusal upgrades, 326 invalid-to-valid STEP corrections and one captain-reviewed refusal change. Each STEP correction passed the direct no-healing STEP gate, raw-invalid before and raw-valid after, and its `evidence.sha256` pins the retained gate report. Rows whose change could not be bisected take their public source from this inventory.

## Merge checks

`tools/checks/rules.json` declares the required jobs independently of workflow
`needs`. `tools/checks/checks.py select` unions the base and candidate rules and
workspace Cargo dependency graphs, including dev, build, optional and
target-specific dependencies. Renames use both paths. Shared build inputs and
unknown paths select every crate. Documentation-only changes still run
formatting and policy checks without a kernel replay.

When all non-documentation changes match the reviewed `ci_paths`, selection runs
the CI tooling checks and only changed job definitions with their required
prerequisites. Job definitions are compared as YAML, including inherited
environment, defaults and permissions. This path never selects test shards or
the 477-case replay. Source changes retain normal selection. Replay inventories,
correction approvals and the raw STEP validator are not CI-only paths.
The selector uses PyYAML 6.0.3, installed in a temporary virtual environment by CI.
Base and candidate rules are still unioned, so the PR introducing this policy
runs the full suite once under the old base rule.

`test-build` compiles the selected release tests once with cargo-nextest 0.9.148,
runs the selected documentation tests, and uploads a one-day nextest archive.
The four `tests` shards consume that archive with `slice:k/4` partitions and
four test threads each. Build jobs also use four Cargo workers. Shards extract
into the checkout so compile-time `CARGO_BIN_EXE_*` paths still resolve to the
archived CLI binaries. The existing ten-minute nextest hang guard remains in
`.config/nextest.toml`.

`build` publishes the verifier without waiting for OpenCASCADE regressions.
`step-regressions`, `replay` and `scoreboard` then consume that same verifier
independently. Under normal source selection, the final gate requires both new
jobs whenever their original tests or build checks were selected. STEP evidence
must match the build's binary digest. Replay execution and comparison rules are
unchanged.

Run `ci/bootstrap` once to install the pre-push lint hook through this
repository's local `core.hooksPath=ci/hooks` setting. It needs no sudo and changes
no global Git configuration or shell dotfiles. `ci/run lint` runs the same
formatting, check-policy, edge-hunt, release-policy and workspace Clippy commands
used by CI. The workflow uses `ci/run fmt` and `ci/run clippy` separately to
retain selected-package routing.

The earlier-answer inventory is `tools/checks/earlier-answers.json`. It retains
all 477 request and accepted-answer digests. Operation families are derived from
the requests; every owner is `unknown`. Changes in the verification binary's
build closure therefore run all 477 at four workers, fresh and without cache
reuse. Target-part and shared verification examples also select their test
consumers. The target-part scoreboard now reports to the same final `check` gate.

The replay job checks out the private proof-input repository at the commit in
the rules, using the read-only `CATALLAX_PROOF_INPUTS_DEPLOY_KEY` Actions secret,
then sparsely checks out only the approved corpus file and verifies its digest
before execution. Judge and survey packs are not checked out. Forks without that credential
cannot satisfy replay. Do not use `pull_request_target` to grant them access.
Public artifacts contain only selection decisions, job identities and aggregate
replay evidence. Inputs, per-case manifests, geometry and question ids stay off
public logs and artifacts.

The final gate rejects missing, cancelled, unexpected, selected-but-skipped or
stale jobs and missing test partitions. Evidence binds the tested merge commit,
head commit, run and attempt, binary, corpus, metadata, correction-list and driver
identities. Replay evidence additionally requires four fresh workers, zero cache
hits and the selected case count. Earlier-answer comparison remains byte-strict
except for the narrow invalid-to-valid STEP correction path below.

`tools/checks/replay-corrections.json` admits only `invalid-to-valid-step`
corrections for indices on the base revision's active known-raw-invalid list.
The before STEP hash must match both the base inventory and its trusted captain
ruling. Each correction pins the request, before and after answer, manifest and
STEP digests, the changed STEP fields, and a digest of the base comparable
manifest without `step.added_edges`, `step.added_vertices`,
`step.max_deviation` and `step.approximated_curves`. Family, owner, request and
other output files cannot change.

That committed digest has no authority on its own. For newly corrected indices,
the selector retains the base inventory rows in the check plan. The build job
checks out the plan's base revision, verifies its clean HEAD and builds a
separate verifier. The replay job runs only those indices through that verifier,
then checks their requests,
answers, STEP files and full comparable manifests against the base inventory
digests, then derives the protected-field digest from the authenticated base
manifest itself. Both the committed digest and the candidate's protected fields
must match that derived value. A candidate cannot authorize its own changed
fields by recomputing its declaration.

The replay summary records `verified_corrections`, which must name every newly
corrected index at the final gate. Unchanged inventories require no base build
or base replay. `checks.py replay` consumes `--plan` and requires `--base-binary`
when that plan contains newly corrected indices. Base manifests stay private.

The replay checks the committed candidate digests. The direct no-healing audit
also requires each corrected file to be a valid single solid, within the default
1e-7 STEP deviation, with its converged imported volume inside the unchanged
certified volume interval widened by imported face area x 1e-7 and integration
spread. Other metadata changes still cannot authorize a new answer.
Release correction rows and release qualification remain separate release work.

The captain's 29 October 2026 option-A ruling, "Go with the recomended",
grandfathers exactly the inherited raw-invalid STEP files at indices 262 and
431, with their exact hashes in `tools/checks/known-raw-invalid.json`. This is
not a validity claim. The direct no-healing audit still checks every selected
STEP output. An unlisted raw-invalid file or changed bytes in a listed file
while it remains raw-invalid fail. A listed file becoming raw-valid is an
approved invalid-to-valid upgrade and must leave the active list.

The ruling's scope is fingerprinted in the checker. A new list entry or an
edited ruling cannot authorize itself. Expansion requires an explicit captain
ruling and a reviewed update of the trusted ruling fingerprint. The selector
validates both policy versions, and job evidence binds the current policy hash.
The policy table covers unchanged inherited failures, new invalid files,
changed invalid bytes, unapproved additions and valid-upgrade removal.

`release.py`, release evidence and packaging retain their existing qualification
contract. Aligning routine-release tiers with the joint milestone plan and adding
a nightly audit are outside this bootstrap.

The observational `timings` job runs after `check` and publishes the
`check-timings` artifact with per-job queue/wall times, time to gate, replay
elapsed time and selection decisions. It cannot measure its own completion.
Record final-head control and planted-fault timings with run/artifact links in
the pull request body, not in a new commit that would change the tested head.

## Generate the replay aggregate

Use the [verification skill](../.claude/skills/verify-catallax/SKILL.md) on the designated replay machine. Raw inputs and per-case artifacts remain there; do not upload them to GitHub, name them in public notes or commit them. `BASELINE`, `CANDIDATE`, `INPUTS` and `PROOF` below are local runtime paths selected by the operator.

```sh
DRIVER=.claude/skills/verify-catallax/scripts/control-catallax.py
python3 -B "$DRIVER" run "$INPUTS" --binary "$BASELINE" --workers 1 --fresh --out "$PROOF/baseline-w1" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 1 --fresh --out "$PROOF/candidate-w1" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 2 --fresh --out "$PROOF/candidate-w2" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 4 --fresh --out "$PROOF/candidate-w4" --json
python3 -B tools/release/release.py replay-summary \
  "$PROOF/baseline-w1/run.json" "$PROOF/candidate-w1/run.json" \
  "$PROOF/candidate-w2/run.json" "$PROOF/candidate-w4/run.json" \
  --out "$PROOF/replay-summary.json"
```

Pass multiple runtime input paths to `run` when needed. The aggregate rechecks saved artifact hashes and runs the driver's strict comparisons itself. It exports counts, source identities and both approval-file SHA-256 values, never input names, paths, recipes or geometry. Summary format `catallax-release-replay/3` records separate `upgrades` and `corrections` counts for the baseline comparison. Any approved difference requires `equal: false`; it is not byte equality. Candidate worker comparisons require `equal: true` without exceptions. Regenerate older summaries rather than relabelling their format.

The command rejects uncommitted approval files. CI checks both file digests and counts against the selected candidate tree and binds the baseline to `replay-corrections.json`'s `baseline_sha`. It rejects stale candidates, incomplete or cached runs, internal errors, changed inputs/allowances and worker-count mismatches. Keep the full per-case proof on the replay machine for audit.

### Approve refusal upgrades

Review each new answer and its saved artifacts before adding an entry. Commit only fingerprints, never input names, paths, recipes, geometry or raw manifests. Each entry has exactly these fields:

| Field | Value |
| --- | --- |
| `index` | Zero-based position in the ordered 477-case replay, including duplicates |
| `request_sha256` | Driver `digest` of `request.json` with only `out` removed; includes the original allowance |
| `refusal_sha256` | `release.answer_digest(driver, baseline_case_directory)` |
| `answer_sha256` | `release.answer_digest(driver, candidate_case_directory)` |

`answer_digest` hashes a JSON object with `manifest` set to the driver's existing `comparable` manifest and `files` containing SHA-256 values for `answer.step`, `display.obj`, `print.stl` and `answer.igs`. Missing files are `null`. The driver hashes canonical UTF-8 JSON with sorted keys, compact separators and `ensure_ascii=False`. Only the existing build identity, statistics and `face_measurements.display.first_mesh_ms` exclusions apply. All other answer content and compared output bytes remain pinned.

The file has format `catallax-replay-upgrades/2` and an `upgrades` array. Version 2 fingerprints also cover IGES. Indices must be unique and in range, and all three digests must be lowercase 64-digit SHA-256 values. The aggregate checks the unchanged request, original refusal and exact new answer against each entry. It never generates approvals automatically. Older fingerprints must be regenerated with the new helper, not relabelled.

### Approve corrected STEP outputs

The correction file has format `catallax-replay-corrections/1`, an immutable selected `baseline_sha` and a `corrections` array. Its baseline must be the approved previous release, not a convenient newer checkpoint. Each row has exactly these fields:

| Field | Value |
| --- | --- |
| `index` | Unique zero-based position in the ordered 477-case replay |
| `class` | `invalid-to-valid-step`, a reviewed invalid earlier STEP repaired into a valid STEP under the unchanged request, or `same-code-refusal-stage` (below) |
| `request_sha256` | Request fingerprint with only `out` removed |
| `before_sha256`, `after_sha256` | `answer_digest` values for the original and corrected answers |
| `manifest_fields` | Exact changed-field set, drawn only from `step.added_edges`, `step.added_vertices`, `step.max_deviation`, `step.approximated_curves`; empty for a byte-only correction |
| `sources` | Nonempty list of `{pr, commit}` objects identifying public correction PR URLs and full source-fix commits |
| `evidence` | `{sha256, before_step_sha256, after_step_sha256}` binding retained independent validation evidence and both exact STEP byte streams |

Both answers and both STEP files must exist. The driver permits only the listed STEP reporting fields and STEP bytes to change. It rejects altered properties, topology/origin results, marks, request settings or any OBJ, STL or IGES change, even if a full answer fingerprint was listed. Export-added entity counts do not establish model-topology changes. Changed refusals and valid-to-different-valid exports are not corrections of this class.

A `same-code-refusal-stage` row records a refusal that keeps its code but now stops at a different step or Boolean stage. It has the same fields except `evidence`, because a refusal publishes no STEP. `before_sha256` and `after_sha256` are the `answer_digest` values of the two refusals. `manifest_fields` is the exact nonempty changed set, drawn only from `refusal.step`, `refusal.stage` and `refusal.detail`. The driver requires both cases to be refusals with the same code, no output file on either side and every other manifest field unchanged. A refusal that changes its code fails unless it has a `reviewed-refusal-change` row.

A `reviewed-refusal-change` row records a refusal whose code changed and which the captain reviewed individually. It has the same fields as a refusal-stage row. `manifest_fields` must include `refusal.code` and may add only `refusal.step`, `refusal.stage`, `refusal.detail` and `question_id`. Both cases must be refusals with no output file on either side. A refusal that keeps its code cannot use this class.

The committed row is a reviewer attestation, not an automatic geometry verdict. Before approval, validate the baseline invalidity and the candidate's finite trims, material, applicable error bounds and file topology independently for those exact files. Retain the original grids and probes; do not discard points or change tolerances. Evidence hashes pin that review and must identify these STEP subjects. Unknown validity or equivalence remains a release hold. Do not commit private case contents, identifiers, machine paths or checker details.

After reviewed entries land, rebuild and replay the complete candidate freshly at one, two and four workers before generating the exact-source summary. Do not put the eventual candidate commit into its own committed approval data: derive it from the rebuilt manifests, while the summary binds the approval-file digests. Adding an approval or changing source invalidates affected earlier candidate evidence.

At a clean candidate commit on the versioned release branch, submit only the generated public JSON:

```sh
SHA=$(git rev-parse HEAD)
SUMMARY=$(cat "$PROOF/replay-summary.json")
gh-axi workflow run release-evidence.yml -R BohnBawerick/catallax \
  --ref release/0.1.1 --field "replay_summary=$SUMMARY"
gh-axi run list -R BohnBawerick/catallax --workflow release-evidence.yml --commit "$SHA"
```

Dispatch uses a branch or tag, not an unreferenced commit SHA. If the release branch moves after the replay, the commit gate fails closed; replay and prepare evidence for the new candidate. Unrelated development on `main` does not move the release candidate.

The successful run uploads `release-evidence-SHA` for 90 days. Record its run ID as `EVIDENCE_RUN`. If it expires, rerun the evidence workflow with the saved aggregate at the same commit. The tag workflow automatically selects the latest successful `release-evidence.yml` run for its exact commit and validates both evidence files again. It never substitutes an older committed milestone report.

## Dry run without publishing

After the workflows land and the candidate release branch exists:

```sh
gh-axi workflow run release.yml -R BohnBawerick/catallax \
  --ref release/0.1.1 --field "evidence_run=$EVIDENCE_RUN"
```

`workflow_dispatch` has no publish switch. It always builds and attests the same files, and never creates a GitHub Release or pushes a tag. Only a tag-push event can enter the publishing job. Dry runs skip the release-branch ancestry, milestone-note and green-release-CI gates, so release preparation can be exercised before a milestone is complete.

For a branch introducing or changing the release workflows, GitHub cannot dispatch a new workflow file until that file exists on the default branch. The existing `check.yml` provides the bootstrap entry point and runs the full suite too:

```sh
gh-axi workflow run check.yml -R BohnBawerick/catallax \
  --ref fm/catallax-release-machinery --field release_dry_run=true \
  --field "replay_summary=$SUMMARY"
```

This first generates the scoreboard at the tested commit, then calls the reusable release workflow with that same run's artifact. A non-publishing dry run may reuse a previously measured replay aggregate after a mechanical rebase or CI-only change. Its original `candidate_sha` remains in the attached JSON and logs; it is not relabelled as a replay of the dry-run commit. The scoreboard must still match the current commit and recipe hashes. Ordinary standalone `release-evidence.yml` dispatch and every tag-push release require exact-commit replay evidence. Before a real release, run a fresh replay on the final release-branch commit after its fixes land. All build failures remain failures. A dry run is not a release.

## Cut a release

After every checklist item is satisfied, from the checked versioned release branch:

```sh
VERSION=$(cargo metadata --no-deps --format-version 1 | python3 -c 'import json,sys; m=json.load(sys.stdin); print(next(p["version"] for p in m["packages"] if p["name"] == "catallax-cli"))')
git tag -a "v$VERSION" -m "Catallax $VERSION alpha"
git push origin "v$VERSION"
gh-axi run list -R BohnBawerick/catallax --workflow release.yml
```

The workflow first creates a draft release with all verified files, then makes it public. For 0.x it sets GitHub's prerelease flag and includes `alpha` in the title. If publication fails after draft creation, inspect that draft before retrying; never move its tag or overwrite published files.

## Tool maintenance

Update the cargo-dist version in `dist-workspace.toml` and both pinned upstream installer URLs in `release-build.yml` together. The workflow uses cargo-dist's GitHub release installers rather than assuming every GitHub release is also published to crates.io. `ci = []` is deliberate: cargo-dist owns platform archives, while the checked-in workflows own evidence, milestone gates, SBOM generation, universal assembly and the non-publishing dispatch path. Compilation and attestation jobs have contents-read tokens. An isolated notes job needs contents-write for GitHub's generate-notes API, even though that API saves no release; only the tag wrapper invokes release creation. Upstream [universal binary support](https://github.com/axodotdev/cargo-dist/issues/77) is still open, so `universal.py` joins the macOS slices. Like cargo-dist's generated workflow, assembly invokes cargo-cyclonedx explicitly; `dist build --artifacts=global` alone declares the SBOM but does not generate it. GitHub's [generated release notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes) supply the merged-PR list.

The installers use a job-local unmanaged directory. Unmanaged mode deliberately does not update PATH, so both platform steps explicitly export that directory through `GITHUB_PATH` for later build steps.

After changing this machinery, run the policy tests and actionlint, then exercise the entire dry run. A plan-only or Linux-only build does not prove the release works.
