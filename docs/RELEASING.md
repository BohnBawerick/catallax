# Milestone releases

Catallax releases follow completed work, not dates. M1 is **0.1.0**. Each later roadmap milestone advances the minor version, so M2 is 0.2.0 and M3 is 0.3.0. Patch versions, such as 0.1.1, fix an already released milestone without claiming the next milestone. The entire 0.x series is labelled **alpha** and published as GitHub prereleases. A version number never encodes a date. The first 1.x release needs a separate readiness decision.

No release is scheduled by this machinery. A maintainer pushes a `vX.Y.Z` tag only after the checklist passes. The tag must match `workspace.package.version` in `Cargo.toml` and point to a commit reachable from `main`. Do not move a published tag. Fix a bad release with a new patch version.

## Downloads

`cargo-dist` 0.33.1 packages the existing CLI crate. Each archive contains `catallax`, `catallax-verify`, the existing `exact-brep` compatibility program, README and MIT licence.

| Platform | Artifact |
| --- | --- |
| Linux x86_64, glibc | `catallax-cli-x86_64-unknown-linux-gnu.tar.xz` |
| Linux aarch64, glibc | `catallax-cli-aarch64-unknown-linux-gnu.tar.xz` |
| macOS universal, arm64 and x86_64 | `catallax-cli-universal2-apple-darwin.tar.xz` |
| macOS arm64 | `catallax-cli-aarch64-apple-darwin.tar.xz` |
| macOS x86_64 | `catallax-cli-x86_64-apple-darwin.tar.xz` |
| Windows x64 | `catallax-cli-x86_64-pc-windows-msvc.zip` |

Linux x86_64 builds on Ubuntu 22.04; aarch64 builds on Ubuntu 24.04. These are dynamically linked glibc builds, not musl binaries. Older glibc compatibility is not claimed. Platform jobs extract the archives and run the actual commands, build a block, export STEP and replay the portable question with identical STEP bytes. The universal job joins the two macOS builds with `lipo`, checks both slices with `lipo FILE -verify_arch arm64 x86_64` and exercises each through `arch` on Apple Silicon with Rosetta.

macOS downloads are not Developer ID signed or notarized. The universal executables use only the ad-hoc signature needed for Apple Silicon execution. Windows downloads are not Authenticode signed. GitHub provenance attestations do not replace platform code signing. No crates.io, package-manager or SolidDraft release is part of this workflow.

Every release also attaches:

- `catallax-cli.cdx.xml`, a dependency SBOM generated by cargo-cyclonedx 0.5.9 across all targets. `sbom.py` replaces machine-local workspace references with commit-qualified repository IDs and checks that dependency edges still resolve.
- `replay-summary.json`, a generated 477-input aggregate, with baseline and candidate commit identities, binary hashes, outcomes, work, preservation results and the committed upgrade-list digest.
- `target-parts.json`, generated at the tagged commit with the fixed 1,000,000-unit allowance and OpenCASCADE STEP imports.
- `RELEASE_NOTES.md`, generated from merged pull requests by GitHub's release-notes generator, with alpha, format-compatibility and verification notices. Do not maintain a hand-edited CHANGELOG.
- `SHA256SUMS`, covering all other attached files. Every attached file, including `SHA256SUMS`, gets a GitHub build-provenance attestation.

Verify an individual download with `gh attestation verify FILE --repo BohnBawerick/catallax`. After downloading all assets, run `sha256sum --check SHA256SUMS`, or use an equivalent SHA-256 tool on macOS or Windows. Hashes detect corruption; verify provenance to establish which repository and workflow built the file.

## Release checklist

1. Complete the milestone's must-show list in [PLAN section 10.1](PLAN.md#101-milestones). Land or park every in-flight lane. Rebase pending release changes onto current `main`.
2. Set the workspace version and refresh `Cargo.lock` with Cargo. No milestone bump is made merely to install the machinery.
3. Add `docs/milestones/MN.md`, such as `M1.md`, as required by PLAN item 21. Record landed and parked work, reasons, P0 and target-part numbers including regressions, and the next milestone's must-show list. Patch releases update that milestone's note.
4. Merge the version and milestone note. Require a green full-suite `check.yml` run on that exact `main` commit. The tag workflow rejects a commit without one.
5. On the replay machine, build baseline and candidate verification programs and use the verification driver for the full 477 inputs. Preserve every earlier answer's manifest and strict STEP bytes, the original inputs and work allowances. Run baseline at one worker and the same candidate binary freshly at one, two and four workers. No cache hits, missing manifests or internal errors are allowed. The only permitted baseline differences are explicitly approved refusal-to-answer upgrades. Candidate worker runs must remain strictly equal.
6. Generate the public aggregate as below, then run the evidence workflow on the exact candidate commit. It generates the target scoreboard independently in CI. Inspect refusals, edits, STEP imports and not-run checks; the scoreboard is not proof of complete SolidDraft acceptance.
7. Run the non-publishing release dry run against that commit and evidence run. Inspect all platform smoke checks, SBOM, generated notes, checksums and attestations. Link the green run in the release preparation PR or milestone review.
8. Only then create and push the release tag from `main`. Watch the release workflow. It publishes only after every platform, universal archive, evidence gate and attestation succeeds.

Measurement, comparisons and evidence aggregation live in scripts and CI. None runs in the kernel's part-building path or adds work to a user edit. Never increase a work allowance or loosen a tolerance to make a release gate pass.

For an `X.Y.0` milestone release, use the previous release tag as the replay baseline. When no earlier release exists, use the main commit immediately before the version-and-milestone-note merge, the release commit's first parent. That first-release merge must change only release metadata and documentation, not kernel code or recipes. Record the selected baseline and why in the milestone review. Per-change preservation replays remain the cumulative evidence for the kernel work preceding that baseline.

Every changed baseline case must have been `refused` and now be `answered`, with an entry in the committed `tools/release/replay-upgrades.json`. Changed answers, answers becoming refusals, changed refusals and unlisted upgrades fail. Unchanged refusals remain refusals, not successful answers. The list must describe exactly the upgrades against the selected baseline, with no unused entries. Keep it empty for releases without upgrades.

## Generate the replay aggregate

Use the [verification skill](../.claude/skills/verify-catallax/SKILL.md) on the designated replay machine. Raw inputs and per-case artifacts remain there; do not upload them to GitHub, name them in public notes or commit them. `BASELINE`, `CANDIDATE`, `INPUTS` and `PROOF` below are local runtime paths selected by the operator.

```sh
DRIVER=.claude/skills/verify-catallax/scripts/control-catallax.py
python3 -B "$DRIVER" run "$INPUTS" --binary "$BASELINE" --workers 1 --fresh --out "$PROOF/baseline-w1" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 1 --fresh --out "$PROOF/candidate-w1" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 2 --fresh --out "$PROOF/candidate-w2" --json
python3 -B "$DRIVER" run "$INPUTS" --binary "$CANDIDATE" --workers 4 --fresh --out "$PROOF/candidate-w4" --json
python3 -B tools/release/release.py replay-summary \
  "$PROOF/baseline-w1/run.json" "$PROOF/candidate-w1/run.json" \
  "$PROOF/candidate-w2/run.json" "$PROOF/candidate-w4/run.json" \
  --out "$PROOF/replay-summary.json"
```

Pass multiple runtime input paths to `run` when needed. The aggregate command rechecks saved artifact hashes and runs the driver's strict comparisons itself. It derives commit identities from the saved manifests and exports counts and the upgrade-list SHA-256 rather than case IDs, paths, recipes or geometry. Summary format `catallax-release-replay/2` records the baseline comparison's `upgrades` count separately from `equal`; a permitted upgrade does not claim byte equality. Candidate worker comparisons still require `equal: true`. Regenerate older summaries with this policy rather than relabelling their format.

The command rejects uncommitted upgrade-list changes. CI checks that the summary's upgrade-list digest and count match the file at the selected commit. It also rejects a stale candidate, incomplete replay, cached run or worker-count mismatch. Keep the full per-case proof on the replay machine for audit.

### Approve refusal upgrades

Review each new answer and its saved artifacts before adding an entry. Commit only fingerprints, never input names, paths, recipes, geometry or raw manifests. Each entry has exactly these fields:

| Field | Value |
| --- | --- |
| `index` | Zero-based position in the ordered 477-case replay, including duplicates |
| `request_sha256` | Driver `digest` of `request.json` with only `out` removed; includes the original allowance |
| `refusal_sha256` | `release.answer_digest(driver, baseline_case_directory)` |
| `answer_sha256` | `release.answer_digest(driver, candidate_case_directory)` |

`answer_digest` hashes a JSON object with `manifest` set to the driver's existing `comparable` manifest and `files` containing SHA-256 values for `answer.step`, `display.obj` and `print.stl`. Missing files are `null`. The driver hashes canonical UTF-8 JSON with sorted keys, compact separators and `ensure_ascii=False`. As in strict comparisons, only build identity, statistics and `face_measurements.display.first_mesh_ms` are excluded from manifest equality. All answer content and output bytes remain pinned.

The file has format `catallax-replay-upgrades/1` and an `upgrades` array. Indices must be unique and in range, and all three digests must be lowercase 64-digit SHA-256 values. The aggregate checks the unchanged request, original refusal and exact new answer against each entry. It never generates approvals automatically. After committing reviewed entries, rebuild the candidate and replay all cases at all worker counts from that commit before generating the public summary.

At a clean candidate commit on `main`, submit only the generated public JSON:

```sh
SHA=$(git rev-parse HEAD)
SUMMARY=$(cat "$PROOF/replay-summary.json")
gh-axi workflow run release-evidence.yml -R BohnBawerick/catallax \
  --ref main --field "replay_summary=$SUMMARY"
gh-axi run list -R BohnBawerick/catallax --workflow release-evidence.yml --commit "$SHA"
```

Dispatch uses a branch or tag, not an unreferenced commit SHA. If `main` moves after the replay, the commit gate fails closed; replay and prepare evidence for the new tip.

The successful run uploads `release-evidence-SHA` for 90 days. Record its run ID as `EVIDENCE_RUN`. If it expires, rerun the evidence workflow with the saved aggregate at the same commit. The tag workflow automatically selects the latest successful `release-evidence.yml` run for its exact commit and validates both evidence files again. It never substitutes an older committed milestone report.

## Dry run without publishing

After the workflows land on `main`:

```sh
gh-axi workflow run release.yml -R BohnBawerick/catallax \
  --ref main --field "evidence_run=$EVIDENCE_RUN"
```

`workflow_dispatch` has no publish switch. It always builds and attests the same files, and never creates a GitHub Release or pushes a tag. Only a tag-push event can enter the publishing job. Dry runs skip the main-ancestry, milestone-note and green-main gates, so release preparation can be exercised before a milestone is complete.

For a branch introducing or changing the release workflows, GitHub cannot dispatch a new workflow file until that file exists on the default branch. The existing `check.yml` provides the bootstrap entry point and runs the full suite too:

```sh
gh-axi workflow run check.yml -R BohnBawerick/catallax \
  --ref fm/catallax-release-machinery --field release_dry_run=true \
  --field "replay_summary=$SUMMARY"
```

This first generates the scoreboard at the tested commit, then calls the reusable release workflow with that same run's artifact. A non-publishing dry run may reuse a previously measured replay aggregate after a mechanical rebase or CI-only change. Its original `candidate_sha` remains in the attached JSON and logs; it is not relabelled as a replay of the dry-run commit. The scoreboard must still match the current commit and recipe hashes. Ordinary standalone `release-evidence.yml` dispatch and every tag-push release require exact-commit replay evidence. Before a real release, run a fresh replay on final `main` after the queue lands. All build failures remain failures. A dry run is not a release.

## Cut a release

After every checklist item is satisfied, from updated `main`:

```sh
VERSION=$(cargo metadata --no-deps --format-version 1 | python3 -c 'import json,sys; m=json.load(sys.stdin); print(next(p["version"] for p in m["packages"] if p["name"] == "catallax-cli"))')
git tag -a "v$VERSION" -m "Catallax $VERSION alpha"
git push origin "v$VERSION"
gh-axi run list -R BohnBawerick/catallax --workflow release.yml
```

The workflow first creates a draft release with all verified files, then makes it public. For 0.x it sets GitHub's prerelease flag and includes `alpha` in the title. If publication fails after draft creation, inspect that draft before retrying; never move its tag or overwrite published files.

## Tool maintenance

Update the cargo-dist version in `dist-workspace.toml` and both pinned upstream installer URLs in `release-build.yml` together. The workflow uses cargo-dist's GitHub release installers rather than assuming every GitHub release is also published to crates.io. `ci = []` is deliberate: cargo-dist owns platform archives, while the checked-in workflows own evidence, milestone gates, SBOM generation, universal assembly and the non-publishing dispatch path. Compilation and attestation jobs have contents-read tokens. An isolated notes job needs contents-write for GitHub's generate-notes API, even though that API saves no release; only the tag wrapper invokes release creation. Upstream [universal binary support](https://github.com/axodotdev/cargo-dist/issues/77) is still open, so `universal.py` joins the macOS slices. Like cargo-dist's generated workflow, assembly invokes cargo-cyclonedx explicitly; `dist build --artifacts=global` alone declares the SBOM but does not generate it. GitHub's [generated release notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes) supply the merged-PR list.

The installers use a job-local unmanaged directory. Unmanaged mode deliberately does not update PATH, so both platform steps explicitly export that directory through `GITHUB_PATH` for later build steps.

After changing this machinery, run the policy tests and actionlint, then exercise the entire dry run. A plan-only or Linux-only build does not prove the release works.
