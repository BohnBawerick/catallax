## 2026-11-21: mesh Boolean and decimation recipe operations

Pieces: recipe, import, features, application, field
Change: `catallax_recipe::Operation` gains `MeshBoolean { kind, target, tool }` and `MeshDecimate { body, triangles }`, written `"op": "mesh_boolean"` and `"op": "mesh_decimate"` and accepted only in `catallax-recipe/5` ([RECIPE.md sections 4.21 and 4.22](../../RECIPE.md#421-mesh-booleans)). Their inputs must be `import_mesh`, `mesh_boolean` or `mesh_decimate` steps; anything else is a recipe error, as is a triangle count of zero. Both build in the exact evaluators. `catallax_import::mesh` gains `boolean::boolean`, `decimate::decimate`, `ClosedMesh::from_parts` and `ClosedMesh::placed`. New refusal codes: `mesh-boolean.coplanar`, `mesh-boolean.non-manifold`, `mesh-boolean.internal`, `mesh-decimate.crossing` and `mesh-decimate.internal`. Neither operation makes faces; result faces keep the origins of the `import_mesh` steps their triangles came from.
Why: roadmap 3.4, tools only SMLib has: a first build of mesh Booleans and decimation, after SMLib's `SmPolyMerge::ManifoldBoolean` and `SmPolyDecimate::DoQuadricDecimation`.
Migration: `Operation` is `#[non_exhaustive]`, so callers that match it already have a fallback arm. A caller that lists operations which make no faces adds the two. The field kernel refuses both with `field.unsupported-operation`, so a print of their results refuses, and the two-kernel comparison reports them as not comparable.
