## 2026-11-21: the STEP writer's curve fit is counted, not charged

Pieces: 1 (numbers), 7 (step), judge interface (`catallax-verify` responses).
Change: `catallax_numbers::OperationWork` gains `uncharged: u64`, and the new `catallax_numbers::count_exact_arithmetic(a, b, multiply)` adds to it what `Decider::reserve_exact_arithmetic` would charge for the same rational operation. Nothing is charged: `used`, `exhausted`, the allowance and every refusal stay as they were. `catallax-step` counts every exact rational sum, difference, product and quotient of `fit.rs` this way, and a `catallax-response/1` `work` object gains `uncharged`.
Why: Checkpoint 2 decision Q13, predictor step 1 ([section 4.5](../checkpoints/checkpoint-2-decisions.md#45-item-30b-one-model-and-the-predictor)): "Charge work in `catallax-step/src/fit.rs` by limb product, as the decider does." The fit ran uncounted, so an export that took 8.5 s reported 807k work. A charge against the allowance was built first and changed answers: one frozen request and six STEP regression requests that answer today refused `numbers.operation-budget`. The owner ruled on 21 Nov 2026 that the fit is counted in its own counter beside `used` and not charged to it. The written curve has no cheaper construction for a cap to fall back to (predictor step 5).
Migration: code that builds an `OperationWork` value adds `uncharged: 0`. A reader that wants a request's cost at the kernel's rate adds `used`, `refunded` and `uncharged`. The count is the same at any thread count: a helper thread's count reaches the request only with a record the request adopts (`Charges::adopt`), and an `OperationTask` item reports its count as it reports `refunded`.
